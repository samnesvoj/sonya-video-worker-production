Дата: 2026-11-07 · ветка `perf/fast-start` (PR #2, поверх PR #1) · ничего не слито в `main`, не опубликовано, платные Instance не запускались, VPS не менялись.

**Легенда (не смешивать):**
**[ИЗМЕРЕНО-CI]** — измерено на x86-раннере GitHub Actions (без GPU, не на Vast) · **[ФАКТ]** — из официальной документации/репозиториев с источником · **[РАСЧЁТ]** — арифметика от измеренных величин и допущений · **[ДОПУЩЕНИЕ]** — число, которого у нас нет · **[НЕ ПРОВЕРЕНО]** — требует настоящего GPU/Vast. Ни один прогноз ниже не является измерением старта на Vast.

## 1. Итог и рекомендация (по приоритетам: надёжность → ожидание пользователя → стоимость → простота)

1. **Оставить текущий образ как основной** (Debian + Python 3.11, зависимости из lock с хешами, теперь **3 отдельных слоя**). Он собирается, проходит все проверки безопасности и внутриобразные проверки в CI. Это самый надёжный вариант: ничего не меняется в версиях ffmpeg/Python/CUDA, поведение режимов то же.
2. **Главный рычаг ожидания — не холодный старт, а его отсутствие.** RESUME остановленного инстанса пропускает pull образа, скачивание релиза и (после первой загрузки) моделей. Расчётно RESUME ≈ 15–40 с против 3–10 мин у CREATE ([РАСЧЁТ], см. §5). Поэтому: держать остановленный диск 30 минут (`SONYA_STOPPED_RETENTION_SECONDS=1800`, уже по умолчанию), следить за долей RESUME против CREATE по новым метрикам.
3. **Модели — вторая по величине статья времени, и пока неизвестная.** Размер моделей и скорость Timeweb S3 → хосты Vast не измерены; при 5 ГБ и 25 МБ/с это ≈ 3,3 мин [РАСЧЁТ] — столько же, сколько весь pull образа. Внедрён параллельный загрузчик с проверкой SHA-256 (он же устраняет дефект надёжности: оборванный файл больше не считается «скачанным»). Нужны: заполнить `models.lock.json` и измерить скорость с настоящего хоста.
4. **Эксперименты, которые стоит замерить в первом же GPU-тесте (дёшево, ≈ $0.1–0.3 сверху):** (а) время pull нашего образа на 3–5 разных хостах; (б) вариант на базе `nvidia/cuda` (гипотеза: хосты кэшируют такие слои; линковка с системными CUDA-библиотеками **уже подтверждена в CI**, §4); (в) скорость S3 → хост; (г) полный таймлайн CREATE и RESUME новыми метриками.
5. **Не делать:** Nydus/eStargz (поддержка на Vast не подтверждена, lazy-pull требует настройки containerd на стороне хоста, которую арендатор не контролирует), запекание моделей в образ (размер неизвестен; каждое изменение модели = пересборка и повторный pull), zstd-слои (версия Docker на хостах неизвестна), rclone/s5cmd в образе до замеров.
6. **Метрики добавлены** (§3), чтобы эти решения принимались по данным, а не по прогнозам.

## 3. Метрики старта (добавлено; проверено тестами, на GPU не запускалось)

Каждый Instance пишет таймлайн (имена стадий + секунды Unix + размеры; **без** значений окружения, токенов, URL, имён пользовательских файлов) в `/run/sonya/timeline.jsonl` и выгружает его в S3 `fleet-metrics/<WORKER_ID>/<epoch>.json` (по паре PUT: после готовности и при начале первого видео). Центральный dispatcher читает его (`dispatcher/startup_metrics.py`) и склеивает с журналом жизненного цикла и временем постановки задания:

| Стадия | От → до | Источник |
|---|---|---|
| создание Instance | запрос в Vast → Vast сообщил `running` (поиск оффера, **pull образа**, создание контейнера) | журнал dispatcher |
| старт контейнера | `running` → `entrypoint_start` | журнал + метка (включает сдвиг часов) |
| скачивание Worker | `entrypoint_start` → `bootstrap_done` (+ признак `release_cached`) | метки |
| preflight | `run_worker_start` → `preflight_done` | метки |
| загрузка моделей | `models_start` → `models_done` (байты, статусы cached/verified) | метки |
| инициализация CUDA | `cuda_init_start` → `cuda_init_done` (**реальный** контекст + матричное умножение, а не только `is_available()`) | метки |
| readiness | `preflight_done` → `readiness_ok` | метки |
| prewarm воркера | `worker_started` → `prewarm_done` (импорты режимов + контекст CUDA в процессе воркера) | метки |
| ожидание задания | `prewarm_done` → `first_job_claimed` | метки |
| claim → обработка | `first_job_claimed` → `first_job_processing` (скачивание входа из S3) | метки |
| **ожидание пользователя** | постановка задания → `first_job_processing` | очередь + метки |
`summarize()` даёт p50/max отдельно для «холодных» (`release_cached=false`) и «возобновлённых» запусков. Отрицательные интервалы из-за расхождения часов зажимаются в 0 и помечаются. Это инструмент измерения: **настоящих измерений пока нет**.

## 5. STOP/RESUME против DESTROY/CREATE по скорости (с учётом остановки через 60 с)

Все времена — **[РАСЧЁТ]** из измеренного размера образа (3,75 ГБ по сети / 7,48 ГБ распаковано) и допущений; настоящих замеров на Vast нет. Метрики §3 заменят это данными.

| Этап | CREATE (новый Instance) | RESUME (остановленный той же версии) |
|---|---|---|
| поиск оффера + вызов create / start | 5–15 с [ДОПУЩЕНИЕ] | 1–3 с |
| ожидание GPU | — | обычно сразу; **если GPU занят — `scheduling`, Vast: «>30 с — вероятно занят», ожидание может быть бесконечным** [ФАКТ]; у нас таймаут 90 с → отмена → CREATE |
| pull + распаковка образа | 56–112 с при 100–50 МБ/с, ≈ 3,1 мин при 25 МБ/с (таблица ниже) | **нет** (контейнер и слои уже на диске) |
| старт контейнера | 3–10 с [ДОПУЩЕНИЕ] | 3–10 с |
| скачивание релиза по SHA | ≈ 1–3 с (на раннере GitHub 0,9 с [ИЗМЕРЕНО-CI]) | **нет** (релиз проверен на диске, токен не нужен) |
| preflight | 1–3 с | 1–3 с |
| модели | **M ГБ / скорость** (таблица ниже) | **≈ 0** (sidecar `.verified`, без повторного хеширования) |
| CUDA + prewarm | 7–18 с | 7–18 с |
| ожидание claim | ≤ 5 с | ≤ 5 с |
| **Итого (без моделей)** | **≈ 1,5–4 мин** | **≈ 15–45 с** (+ риск `scheduling`) |
| Стоимость ожидания | GPU не тарифицируется при «Loading» [ФАКТ]; тарифицируется время после `running` | то же; остановленный диск тарифицируется (≈ $0.53/сут за 80 ГБ) |

Что это значит при остановке через 60 с: каждое видео, пришедшее позже чем через минуту после предыдущего, платит RESUME (≈ 15–45 с), а спустя 30 минут — CREATE (минуты). Если много повторных видео в окне 5 минут, рычаг #10 (увеличить простой) дешевле, чем кажется (≈ 1,1 ₽ за пробуждение на RTX 3090), но это решение владельца — по условию остаётся 60 с.

## 6. Модели: загрузка, кэш между запусками, стоимость хранения

- **Сейчас:** `models.lock.json` пуст (моделей и доступа к S3 на MacBook нет; фиктивные значения не подставлялись) → размер и скорость неизвестны. Заполнить: `tools/make_models_lock.py` на машине с доступом к S3.
- **Что сделано:** параллельная загрузка (4 файла × 16 потоков по умолчанию, `SONYA_MODEL_WORKERS`/`SONYA_MODEL_STREAMS`), SHA-256 по lock, `.part` + атомарная замена, повторы с back-off (3), `404` у необязательной модели пропускается, обязательная — останавливает readiness; sidecar `.verified` (размер, mtime, sha) исключает повторное хеширование при RESUME.
- **Варианты повторного использования между запусками** [ФАКТ — документация Vast, 2026-11-07]:
  | Способ | Работает | Цена | Вывод |
  |---|---|---|---|
  | Диск остановленного Instance (RESUME) | да, пока Instance существует (у нас 30 мин) | диск тарифицируется даже остановленным: 80 ГБ ≈ $0.53/сут ≈ 44 ₽/сут (RTX 3090/4090, реальные офферы) | уже работает, ограничено retention |
  | Volume Vast | **только на той же физической машине**, нельзя переносить; размер фиксирован; отдельная оплата за ГБ-месяц | $0.2–0.37 за ГБ-мес по офферам (10 ГБ ≈ $2–3.7/мес ≈ 165–305 ₽/мес) | помогает лишь если новые Instance попадают на ту же машину → привязка к хосту снижает доступность; **не рекомендуется** как основной механизм |
  | Модели в образе | да, но каждый новый хост тянет их снова при pull | увеличивает pull на размер моделей | не рекомендуется до измерений |
  | Ближайшее хранилище (например S3 с бесплатным исходящим трафиком) | уменьшает время загрузки для зарубежных хостов | решение владельца (аккаунт, стоимость) | **измерить скорость Timeweb S3 → хост на GPU-тесте; если низкая — рассмотреть** |
  | Cloud Sync Vast | синхронизация с облаком | — | не нужен: загрузчик уже параллельный и проверяемый |

## 7. Что проверяется в GitHub Actions без GPU / что требует Vast

**Проверено в CI (зелёное на `perf/fast-start`):** сборка образа с тремя слоями; размеры слоёв и сжатого образа (§2); все зависимости импортируются совместно (torch 2.5.1+cu124 / NumPy 2.4.6 / OpenCV 4.14 / mediapipe / ultralytics / faster-whisper); `pip check`; bootstrap по закреплённому SHA из приватного репозитория, отказ на ветку/неизвестный SHA/нет токена; Trailer заблокирован; readiness не открывается; health 503→200; нет EXPOSE, не root, нет исходников и секретов в образе; загрузчик моделей (11 тестов + бенчмарк); метрики и разбор таймлайна (тесты, включая отсутствие секретов в таймлайне); gitleaks по всей истории; `pip-audit` + OSV по torch; для варианта `nvidia/cuda` — сборка, линковка, размеры и тот же набор внутриобразных проверок (все проходят).
**Нельзя проверить без GPU/Vast:** реальное время pull на хостах Vast и доля кэша базовых слоёв; скорость S3 → хост; время `running` → `entrypoint_start`; CUDA init на настоящем драйвере; RESUME: как часто GPU занят; совместимость драйвера (cu124 → хосты с CUDA ≥ 12.4); влияние другого ffmpeg (вариант #5) на качество режимов.

**План замеров на первом GPU-тесте** (в той же платной сессии, `docs/GPU_TEST_PLAN.md`; доп. стоимость ≈ $0.1–0.4 / ≈ 8–33 ₽ [РАСЧЁТ]):
1. CREATE с метриками §3 на 3–5 разных хостах: записать `vast_provision_and_pull`, `models`, `cuda_init`, `user_wait`. Критерий принятия: медиана `request_to_ready` ≤ 4 мин; худший хост ≤ 8 мин, иначе — банить хост.
2. Тот же образ с пустым и с прогретым кэшем (повторный CREATE на том же хосте): оценить, насколько хост кэширует слои.
3. Вариант #5 (`Dockerfile.nvidia` → опубликовать вручную) на тех же хостах: сравнить `vast_provision_and_pull`. Принять только если медиана заметно (≥ 30 %) лучше **и** регрессия `virality`/`beep` на ffmpeg 4.4 чистая.
4. Скорость загрузки моделей из Timeweb S3 (число потоков 8/16/32) и сравнение с `s5cmd` на одном хосте — только если boto3 не укладывается в бюджет.

6. Убедиться, что в таймлайнах и логах нет токенов (grep).

## 8. Безопасность

Ничего из оптимизаций не расширяет доступ: код SONYA по-прежнему только по SHA из приватного GitHub через токен ≤ 1 ч; в образах (оба варианта) нет исходников и секретов — проверяет CI; таймлайн содержит только имена стадий/числа (тест на утечки); загрузчик моделей не логирует ключи/URL; SHA-256 по lock защищает от подмены модели и частично закрывает риск `torch.load` чекпойнтов (см. SECURITY_AUDIT); новых портов нет; образ-эксперимент не публикуется. Prewarm и таймлайн отключаются/безвредны вне production-пути (`SONYA_REQUIRE_READY`).
